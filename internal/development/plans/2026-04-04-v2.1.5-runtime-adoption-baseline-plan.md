- owner: AI Agent

## Objective
建立 `v2.1.5` 的 Step1 契約基線，將 `v2.1.1` 到 `v2.1.4` 已完成的 canonical contract / validator 收斂成單一路徑的 runtime adoption baseline，主路徑固定為 `readiness-inspect`。
本版可引用 shared canonical law，但不吸收 `v2.1.1` 到 `v2.1.4` 的 primary scope；本版只定義第一條最小可用 adoption flow 的 binding、target legality、preflight 與 readiness output shape。

## Acceptance Criteria
1. schema 必須以 machine-checkable 方式定義 `readiness-inspect` command binding，不允許 prose-only fallback。
2. schema 必須限制 target scope 只接受 `canonical_repo_root` 與 `legal_worktree_instance`，不得接受 workspace-level convenience target。
3. schema 必須以顯式引用與 machine-checkable chaining 的方式吸收四段既有 validator chain：tool-command adoption、multi-repo worktree identity、context runtime preflight、session readiness state；不得重新定義或覆寫 `v2.1.1` 到 `v2.1.4` 的 primary scope。
4. fail example 必須同時表達至少一個非法 target 與至少一個 truth / readiness 違規情形。
5. 本版只建立 adoption baseline，不實作 CLI/runtime/frontend/workflow。
6. `version_index.md` 已追加 v2.1.5 Step1 row，狀態為 `UNVERIFIED` 且 `run_ref=N/A (step2-pending)`。

## Out of Scope (Step1)
- 不實作 `readiness-inspect` runtime command。
- 不新增 `workflow_index.md` row，因本版尚未建立 Step2 workflow artifact。
- 不修改 `aaa-tools`、`aaa-tpl-frontend` 或任何 runtime domain code。

## Risks
- 若 `v2.1.5` 不先把四段 law 的 adoption order 固定下來，後續 Step2 很容易重新退化成 ad hoc command flow。
- 若 target scope 放寬到 workspace root 或 arbitrary local path，`v2.1.2` 的 identity law 會在第一條 adoption path 上被直接繞過。

## Triple-Summary Protocol (v2.1.5)
### 1. Strategic Plan (戰略計畫摘要)
先用單一路徑 `readiness-inspect` 驗證四段治理底座可以共同生效，避免一次同時打開多條 runtime path 造成 adoption 範圍失控。

### 2. Schema Evolution (結構演進摘要)
新增 `runtime-adoption-readiness-inspect-bundle.v0.1.schema.json`，固定 command binding、target legality、current truth preflight 與 readiness output 之間的最小 adoption chain。

### 3. Component Architecture (組件架構摘要)
Step1 僅交付 `readiness-inspect` adoption bundle 與 pass/fail fixtures；Step2 再把此 bundle 對應到 `aaa-tools` runtime validator / CLI / workflow。
