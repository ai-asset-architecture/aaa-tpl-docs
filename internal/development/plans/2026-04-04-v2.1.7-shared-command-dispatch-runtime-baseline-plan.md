## Objective
建立 `v2.1.7` 的 Step1 契約基線，將既有 `readiness-inspect` 與 `repo-check` 收斂到 shared command dispatch runtime。
本版可引用 shared canonical law，但不得重新定義、覆寫或吸收 `v2.1.1` 到 `v2.1.6` 的 primary scope；本版只定義 command dispatch plane 的最小可用 routing、output envelope 與 exit semantics。

## Acceptance Criteria
1. schema 必須以 machine-checkable 方式定義 shared dispatch runtime，不允許 prose-only fallback。
2. schema 必須明確限制目前只消費既有 `readiness-inspect` 與 `repo-check` 兩條 command path，不得偷渡 broader command family expansion。
3. 本版只將既有 `command-registry-contract.v0.1.md` runtime-plane 化，不得新增或重寫新的 primary command law。
4. schema 必須固定共同 dispatch routing、output envelope 與 fail-closed exit semantics。
5. fail example 必須表達至少一個未登錄 command path 或一個試圖新增 family expansion 的違規情形。
6. 本版必須明確聲明其僅消費既有 contract，不得出現隱性 primary law 增殖。
7. 本版只建立 runtime baseline，不實作 CLI/runtime/frontend/workflow。
8. `version_index.md` 已追加 `v2.1.7` Step1 row，狀態為 `UNVERIFIED` 且 `run_ref=N/A (step2-pending)`。

## Out of Scope (Step1)
- 不實作 shared dispatch runtime 或 CLI wiring。
- 不新增第三條 runtime adoption consumer。
- 不修改 `aaa-tools`、`aaa-tpl-frontend`、`aaa-evals` 或任何 runtime domain code。

## Risks
- 若 `v2.1.7` 被誤做成新的 command framework law，shared dispatch plane 會反向奪權。
- 若 output envelope 與 exit semantics 不先固定，後續 runtime 仍會保留 path-specific ad hoc behavior。

## Triple-Summary Protocol (v2.1.7)
### 1. Strategic Plan (戰略計畫摘要)
先把前兩條 adoption consumer 收斂到 shared dispatch plane，避免 AAA 繼續長成多條 path 各自直連 runtime 的鬆散結構。

### 2. Schema Evolution (結構演進摘要)
新增 `shared-command-dispatch-runtime-bundle.v0.1.schema.json`，固定 command ref、dispatch entry、共同 output envelope 與 fail-closed exit semantics。

### 3. Component Architecture (組件架構摘要)
Step1 僅交付 shared dispatch baseline bundle 與 pass/fail fixtures；Step2 若啟動，才把此 bundle 對應到 `aaa-tools` 共同 dispatch runtime。
