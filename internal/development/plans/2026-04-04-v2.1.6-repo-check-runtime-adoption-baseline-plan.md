## Objective
建立 `v2.1.6` 的 Step1 契約基線，將 `repo-check` 定義為 shared governance law 的第二條 runtime adoption consumer。
本版可引用 shared canonical law，但不吸收 `v2.1.1` 到 `v2.1.5` 的 primary scope；本版只定義第二條最小可用 adoption flow 的 command binding、target legality、current truth preflight、result shape 與 readiness-consumable relation。

## Acceptance Criteria
1. schema 必須以 machine-checkable 方式定義 `repo-check` command binding，不允許 prose-only fallback。
2. schema 必須限制 target scope 只接受 `canonical_repo_root` 與 `legal_worktree_instance`，不得接受 workspace-level convenience target。
3. schema 必須以顯式引用與 machine-checkable `ref/id` chaining 的方式吸收既有 command/tool、identity、context、readiness law；不得重新定義或覆寫 `v2.1.1` 到 `v2.1.5` 的 primary scope。
4. schema 必須把 result shape 與 readiness-consumable relation 契約化為 machine-checkable 結構，不得只用自由文本描述。
5. `repo-check` 不得以 repo-local heuristic 取代 canonical target resolution、current truth preflight 或 readiness/result contract。
6. fail example 必須同時表達至少一個非法 target、至少一個 truth 違規，以及至少一個 result/readiness 違規情形。
7. 本版只建立 adoption baseline，不實作 CLI/runtime/frontend/workflow。
8. `version_index.md` 已追加 `v2.1.6` Step1 row，狀態為 `UNVERIFIED` 且 `run_ref=N/A (step2-pending)`。

## Out of Scope (Step1)
- 不實作 `repo-check` runtime command 或 validator。
- 不新增 `workflow_index.md` row，因本版尚未建立 Step2 workflow artifact。
- 不修改 `aaa-tools`、`aaa-tpl-frontend`、`aaa-evals` 或任何 runtime domain code。

## Risks
- 若 `repo-check` 回退為 repo-local heuristic，第二條 path 會直接破壞 `v2.1.2` 與 `v2.1.3` 的 target/truth law。
- 若 result shape 與 readiness-consumable relation 未先契約化，後續 Step2 很容易把 `repo-check` 實作成 ad hoc output，而非 governance runtime consumer。
