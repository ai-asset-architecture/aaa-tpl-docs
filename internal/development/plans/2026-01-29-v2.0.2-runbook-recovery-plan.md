修復 nightly governance 在 reindex runbook 失敗（RUNTIME_ERROR）導致夜間流程中斷的問題，補強 runbook runtime 的可診斷性與冪等輸出，並在修復完成後對齊 `aaa-actions` 與 `aaa-tpl-docs` 的 tag 觸發器，最後建立 v2.0.0 tag/release（以主版本名義對外公布）。

## User Review Required
> [!IMPORTANT]
> 1) Runbook runtime 的錯誤輸出結構若有調整，需保證向後相容。
> 2) Tag/Release 對齊需在 nightly 綠燈後執行，避免以失敗狀態釋出。

## Triple-Summary Protocol (v2.0.2)
### 1. Strategic Plan (戰略計畫摘要)
本次以「先修復治理流程再釋出 tag」為主軸。nightly 的 RUNTIME_ERROR 使資料與報告無法穩定產出，若直接發佈 v2.0.0 會造成治理證據斷裂。因此策略採用兩段式：先在 `aaa-tools` 修補 runbook runtime 的可診斷性與穩定性，讓 reindex 失敗可被定位且不會因無輸出而阻斷後續驗證；再以 `aaa-actions` 建立新 tag，確保 nightly 使用最新版工作流；最後才進行 v2.0.0 的對外標記與版本對齊。此流程可確保版本節點具備完整證據鏈與可追溯結果，符合 governance 對「可稽核與可重現」的要求。

### 2. Schema Evolution (結構演進摘要)
此階段不新增外部資料結構，但會強化 runbook runtime 的錯誤輸出結構，至少包含失敗的步驟識別、作用路徑與例外訊息，讓 `RUNTIME_ERROR` 不再只有摘要提示。對於 nightly 報告或 dashboard 的 JSON/HTML schema 不做破壞性更動，以避免下游視覺化或審計工具失效。若新增欄位，將採「附加欄位」策略，確保舊版解析器仍可工作；必要時補充 audit 文件說明欄位意義與預期輸出位置。

### 3. Component Architecture (組件架構摘要)
修復採用三層次協作：
1) `aaa-tools` 修正 runbook 執行器（runtime）在失敗時的診斷輸出與 reindex 行為，確保 failure 可被定位且輸出一致。
2) `aaa-actions` 更新 nightly workflow 使用新版工具與流程，並透過新 tag 管理釋出，以避免 trigger 仍指向舊版行為。
3) `aaa-tpl-docs` 更新 nightly trigger 版本與 audit 證據，確保治理記錄完整且可追溯。
此分層確保「工具 → 流程 → 證據」閉環，在修復完成後再進行 v2.0.0 發佈，避免對外標記與實際治理能力不一致。
