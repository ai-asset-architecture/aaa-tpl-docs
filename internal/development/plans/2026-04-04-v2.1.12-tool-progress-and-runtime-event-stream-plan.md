## Acceptance Criteria
1. schema 必須以 machine-checkable 方式定義 progress/event stream，不允許 prose-only fallback。
2. schema 必須明確區分 progress signal、result signal 與 evidence signal。
3. event stream 屬 runtime signal，不得升格為 canonical truth source。
4. progress signal 不得直接升格為 result / evidence。
5. event stream 可作為 evidence 生成或引用來源之一，但 event stream record 本身不得直接等同正式 evidence artifact，除非經既有 evidence / promotion contract 明確封裝與提升。
6. fail example 必須表達至少一個 progress signal 或 raw stream record 被誤當 result 或正式 evidence artifact 的違規情形。
7. 本版必須明確聲明其僅消費既有 contract，不得出現隱性 primary law 增殖。
8. `version_index.md` 已追加 `v2.1.12` Step1 row，狀態為 `UNVERIFIED` 且 `run_ref=N/A (step2-pending)`，且 `v2.1.11 ~ v2.1.19` Step1 row wording 必須一致。
9. `version_index.md` 的 `status` / `run_ref` / step wording 必須使用 canonical phrase，不得出現同義改寫。

## Out of Scope (Step1)
- 本版只建立 Step1 runtime-plane baseline，不實作 runtime entry / validator / CLI wiring / frontend publish / workflow artifact。
- 不建立 analytics 產品層。
- 不修改 `aaa-tools`、`aaa-tpl-frontend`、`aaa-evals` 或任何 runtime domain code。

## Risks
- 若 progress 與 result 分層不清，後續 workflow 與 operator surface 會被錯誤 runtime signal 污染。
- 若 event stream 被當成 canonical truth，`v2.1.3` 的 truth law 會被繞過。

## Triple-Summary Protocol (v2.1.12)
### 1. Strategic Plan (戰略計畫摘要)
建立 shared execution signal plane，讓後續 workflow、delegation 與 operator surface 可共同消費 progress/event，而不再各自定義執行狀態。

### 2. Schema Evolution (結構演進摘要)
新增 `tool-progress-and-runtime-event-stream.v0.1.schema.json`，固定 progress signal、result signal 與 evidence signal 的分層。

### 3. Component Architecture (組件架構摘要)
Step1 僅交付 progress/event stream bundle 與 pass/fail fixtures；Step2 若啟動，才把此 bundle 對應到 `aaa-tools` event stream runtime。
