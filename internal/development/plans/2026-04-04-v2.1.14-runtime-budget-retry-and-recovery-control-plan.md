## Acceptance Criteria
1. schema 必須以 machine-checkable 方式定義 runtime budget / retry / recovery，不允許 prose-only fallback。
2. schema 必須至少區分 budget envelope、retryable failure、terminal failure、fallback mode 與 stop condition。
3. recovery plane 只處理 runtime control，不得擴成 provider orchestration business layer。
4. schema 或 examples 必須能表達 retry path 與 fallback path 的終止邊界，避免 fallback 被隱性納入無界重試循環。
5. fail example 必須表達至少一個超出 budget 仍持續執行、terminal failure 仍被錯誤重試，或 fallback 被錯誤納入 retry recursion 的違規情形。
6. 本版必須明確聲明其僅消費既有 contract，不得出現隱性 primary law 增殖。
7. `version_index.md` 已追加 `v2.1.14` Step1 row，狀態為 `UNVERIFIED` 且 `run_ref=N/A (step2-pending)`，且 `v2.1.11 ~ v2.1.19` Step1 row wording 必須一致。
8. `version_index.md` 的 `status` / `run_ref` / step wording 必須使用 canonical phrase，不得出現同義改寫。

## Out of Scope (Step1)
- 本版只建立 Step1 runtime-plane baseline，不實作 runtime entry / validator / CLI wiring / frontend publish / workflow artifact。
- 不建立 provider 商業層或配額計費產品面。
- 不修改 `aaa-tools`、`aaa-tpl-frontend`、`aaa-evals` 或任何 runtime domain code。

## Risks
- 若 retry 與 terminal failure 未分層，recovery runtime 很容易失控。
- 若 budget envelope 不先固定，後續 orchestration 與 workflow 執行將難以關閉。
