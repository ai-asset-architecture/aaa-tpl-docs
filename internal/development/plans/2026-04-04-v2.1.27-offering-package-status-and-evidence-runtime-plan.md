## Acceptance Criteria
1. schema 必須以 machine-checkable 方式定義 package status 與 evidence runtime，不允許 prose-only fallback。
2. schema 必須明確拆開 `package_stage`、`package_compliance_status`、`package_runtime_activity`，不得合併成單一 status axis。
3. schema 必須預留 `evidence_refs` 與 status bundle 的對應欄位，不得讓 status/evidence 分裂成兩套真相。
4. prerequisite verdict 不得被直接推定為 package activation、active status 或 completion。
5. fail example 必須表達至少一個單一 status 軸混合多種語義，以及至少一個 narrative-only evidence 的違規情形。
6. 本版必須明確聲明其僅消費既有 contract，不得出現隱性 primary law 增殖。
7. `version_index.md` 已追加 `v2.1.27` Step1 row，狀態為 `UNVERIFIED` 且 `run_ref=N/A (step2-pending)`。
8. `version_index.md` 的 `status` / `run_ref` / step wording 必須使用 canonical phrase，不得出現同義改寫。

## Out of Scope (Step1)

- 若 stage、compliance、runtime activity 不先分層，後續 package status 很容易退回模糊單一狀態。
- 若 evidence refs 不與 status bundle 一起規格化，後續會出現 narrative 與 artifact 兩套真相。
